# 2026-10-28

## 评估"Agent 自动化审核 + 试用验证 + 自动发布/合并 PR"方案

用户提出用 agent 自动化完成：审核 → 试用验证 → 出验证报告 → 通过后自动发布为 tool，并自动合并 PR，自己完全不介入。

**判断：这是目前唯一正解，因为它正面解决 AdSense 被拒的根因（内容缺一手信息）。** 但有前提。

### 三个必须满足的前提（缺一就退化成内容工厂 → scaled content abuse）
1. **闸门必须是"淘汰"不是"改写"**：通过率应控制在 30-40%，拿不到证据就退回、不生成页面
2. **产出必须是证据不是文案**：实测产物截图 + 可量化数据 + 失败记录，禁止 agent 补写营销形容词
3. **自动发布/合并只能作用于白名单**：仅 `content/tools/<已知分类>/<slug>.md`，其它文件永不自动合并

### 三层流水线设计（成本由低到高）
- L1 确定性检查（近零成本，可直接改造现有 `server/routes/api/cron/link-checker.post.ts` 的 HEAD fetch 逻辑）：站点存活、重定向、TLS、套壳/停车场域名、Wayback 年龄、NSFW 过滤
- L2 LLM 比对（便宜）：官网定价页 vs 提交声称是否一致、识别夸大
- L3 浏览器 agent 实操（贵，只对通过 L1+L2 的做）：注册免费额度、跑一次真实任务、产出截图存 R2

### 诚实的能力边界
登录墙 / 验证码 / 付费墙无法规模化突破；过不去的必须标 `unverified` 而非编造内容。15 分钟缮成本的~ LN izard 验证约 $0.1-0.5/次，随提交量线性增长，当前收入为 0 → 纯成本中心。

### 现有代码可直接复用（已核実）
- `server/plugins/scheduled.ts`：4 个 cron（09:00 daily-ops / 03:00 link-checker / 月报 / newsletter）
- schema/init.sql 已有字段：`status`(含 needs_info/rejected)、`verified`、`last_verified`、`reviewed_at`、`reject_reason`、`reviewer_note`、`data_source` —— 数据模型早就为验证流设计好了

### 给用户的排序建议（他时间不多）
**先验证收钱，再建管道。** 否则等于自动化一台亏钱机器。建议先发一封付费意愿邮件验证，有人付款再按上述方案实现。

### 另注
- 建议废除 GitHub PR 作为数据通道，改全部走表单 → D1 → 验证 → 发布
- README 宣称的 "GitHub DA 100 外链" 实际价值接近零（无人访问的仓库里的 md 文件）
- 自动发布第三方内容需加：NSFW 过滤、免责声明、撤下通道、定期重验

## 已实现：scripts/audit-submissions.mjs（L1 确定性筛查器）

用户确认本地自建 agent 无费用支出后可试，已交付第一层。`pnpm audit` 运行。

**实测结果（55 个开放 PR）**：自动淘汰 9 · 需复核 1 · 进入试用环节 45 → **L1 只能吃掉 16% 的队列**，证明必须有 L3 真实试用环节，否则无法保证质量。

### 实现要点 / 踩过的坑
- **不走 GitHub API**：未认证限流 60 次/小时会被打爆。PR 列表降级为解析 `github.com/{repo}/pulls?state=open&page=N` HTML；文件内容走 `github.com/{repo}/pull/{n}.diff`（自动跳转 patch-diff 域名，不占 API 额度）。设了 `GITHUB_TOKEN` 才走 API
- **diff 每行带 `+` 前缀**，直接按行解析 frontmatter 会全失败 → 优先用 raw.githubusercontent 取原始文件，兜底时剥掉 `+`/`-` 前缀
- **反爬状态码 ≠ 死站**：403/429/503 一律降为 MANUAL（hol.org 实测真实浏览器 UA 也 403，是 Cloudflare WAF）
- **网络抖动导致误杀**：单次连接失败就 REJECT 会让两次运行结论不一致 → 传输层失败重试 3 次后才定性。修复后连续两次运行结果完全一致（45/1/9）
- **archive.org 在本沙箱完全不可达**（wayback available 与 CDX 均 http=000，crt.sh 502）→ 必须区分「明确无存档」与「服务不可达」，后者不得参与判定，否则会对全队列误判（初版曾误报 40/40）
- 结果写 `reports/submissions-triage.{json,md}`，PR 内容缓存在 `reports/.audit-cache.json`（已加入 .gitignore）

### 已知环境局限（换机器重跑需注意）
本机网络屏蔽部分域名（如 gumroad 返回 fetch failed 但站点实际存活），因此「不可达」结论在受限网络中可能误判，需在正常网络环境下复核。

## 用户决策：L3 要真实注册测试（不用模拟）

用户希望用自己的测试邮箱真实登录/注册后再按真实情况试用。**方向认可**（否则大部分降级 UNVERIFIED，流水线失效），
但明确反对"单个固定邮箱"的做法，改为「一次性身份工厂」。

### 反对单邮箱的三条硬理由（非道德顾虑，是技术效率）
1. 同一邮箱跨品类短时间批量注册 = 风控典型异常模式，触发二次验证/封号，**成功率反而低于一次性别名**
2. 邮箱是跨站主标识，被标记后全平台风控抬升；自有域名邮箱极端情况牵连整个域名
3. 泄露不可反查，只能整体废弃 → **不可逆**

### 采纳方案（已写入 plan 第四章）
- catch-all 域名 + 每站唯一别名 `tool-<rand>@<专用域名>`，Cloudflare Email Routing 免费路由到主收件箱
- **该域名必须与 aifindr.org 无关**（防止反查回本站 + 招来针对性垃圾注册）
- IMAP 轮询接码（验证链接/6位码，90秒超时）；每站 20 位随机密码；固定 persona，不用真实姓名/电话
- 测试素材一律本地合成，不上传私人文件；凭据库 `reports/.identity-vault.json` chmod 600
- **三条红线：不解验证码 / 不填任何支付信息 / 不传私人文件**（绕过验证码性质不同于批量注册）
- **ToS 闸门（额外收获）**：L2 抓 /terms grep `no automated access|automated means|bot|scraping` → REJECTED。零 LLM、确定性、顺带淘汰一批

### 成功率预期（已向用户说清）
约 3 成免注册可试 + 3 成注册后给额度 + 3-4 成卡验证码/绑卡/风控。
注册机制把 L3 可测范围从 ~30% 提到 ~60%，其余仍必须诚实记 UNVERIFIED。

### 排序决定
身份层在 **P2 引入，不要更早**——P1(L2) 若已淘汰大部分，就不必为会缩小的集合建接码逻辑。

## 交付 3：scripts/lib/identity.mjs（身份层）

用户**最终决策：沿用同一个邮箱，但每天只注册若干个**（拒绝了 catch-all 域名方案）。

### 关键设计：plus 寻址就是「同一个邮箱」
`you+<tag>@gmail.com` —— 同一账号同一收件箱，风控主体不变，**但每封信地址可区分**，
解决了「泄露不可反查」这个唯一不可逆的风险。零配置。catchall 模式代码路径已预留，日后可切。

### 每日配额是硬约束
`IDENTITY_DAILY_QUOTA` 默认 4。**计数基准必须是 issuedAt（签发日）而非 claimedAt** ——
第一版用 claimedAt 导致 gen 永远不限（签发时还没写 claimedAt），实测第 3 个仍能签发，是个假约束。
CLI: `--check` / `--quota` / `--gen <host>` / `--claim <host> --note "..."` / `--wait <host>`

### 其他修正
- persona 改为**全站统一**：同一邮箱却各站换名字反而更像脚本账户
- 密码改为 base64 派生：原 hex-only 密码不满足站点「大小写混合」策略要求
- persona 曾因共用 hash 前缀导致不同 host 撞同一个人格，改为独立派生路径

### 环境限制
`npx pnpm add -D imapflow` 与 `npm i imapflow` **均被沙箱拦截**（pnpm store 文件读取被拒）。
imapflow 需用户在本地终端自行安装；未安装时 waitForSecret 返回 'no-client' 并给出安装提示，不崩溃。
