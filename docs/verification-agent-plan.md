# 验证型 Agent 实施计划

> 目标：让每台新进的免费工具提交，都必须产出**官网首页上拿不到的一手证据**才允许发布。
> 拿不到证据的一律不发布。不做文案润色，不做内容生成。

## 一、一句话原则

**这是一个淘汰机器，不是写作机器。**
如果最后它变成"把每份提交改写得更好看"，那它只是内容工厂的自动化版——AdSense 上次判 low value content，下次就是 scaled content abuse。

## 二、已确认的本地环境（全部零成本）

| 组件 | 状态 |
|---|---|
| Playwright | 1.60.0，已在 `node_modules` |
| 浏览器内核 | 必须使用本机 Chrome：`/Applications/Google Chrome.app/Contents/MacOS/Google Chrome` |
| Playwright 自带 chromium | **不可用**（1223 缺 headless shell，1187 版本落后），必须显式传 `executablePath` |
| Claude CLI | `/usr/local/bin/claude` v2.1.212，可作为可选推理层，走现有订阅 |
| 实测 | `vocalseparator.com` 抓取成功，标题与截图均正常返回 |

`playwright` 尚未写进 `package.json` 的 dependencies，需补上，否则换机重装会缺。

## 三、四层闸门

### L1 确定性筛查 —— 已交付
`scripts/audit-submissions.mjs`，约 40 秒跑完 55 条。**实测：淘汰 9，存活 46。**

结论很重要：这 46 个站点**真的活着**。它们的问题不是"假"，而是"没价值"。
所以 L1 只能省掉 16% 的眼力，**真正的筛选压力全部压在 L2 和 L3 上**。

### L2 零 LLM 取证 —— 下一步就做这个
纯 HTTP + 静态解析，不调用任何模型。每条约 3 秒，46 条约 3 分钟。

每个站点提取这些事实：

| 维度 | 判定意义 |
|---|---|
| 是否有 `/pricing` `/terms` `/privacy` `/contact` | 四缺三 → 大概率是临时套壳站 |
| 正文可见文本量（去 script/style 后） | < 300 词且自称 AI 工具 → 空壳落地页 |
| 是否单页无敌链接结构（sitemap.xml 只有 1 条） | 典型的 ad-hoc 微站 |
| Google Analytics / GTM ID 是否与其他提交重复 | 同一运营者在批量铺站 |
| 页面 HTML fingerprint（同一套 landing 模板） | 批量生成的姊妹站 |
| 是否引用了真实 AI 供应商域名（openai / anthropic / replicate / stability / fal / together） | **最强的正信号**：证明它真在调模型，不是纯表单壳 |
| `robots.txt` 是否全域 Disallow | 说明它自己都不想被抓 |
| OG title / description 与提交文案是否一致 | 提交者有没有夸大 |

**这一步的意义是决定性的**：如果 L2 能把 46 砍到 15 以下，L3 的代价就可控；
如果砍不动，说明这批站表面都合格，那 L3 是唯一出路，但仍然得先看 L3 的证据质量再决定要不要铺开。

#### L2 实测结论：它不是筛选器，是事实采集器（重要修正）

原以为 L2 能砍掉一大半。**实测 46 个站点只淘汰 2 个**——`reports/evidence-probe.json` 显示
这些站平均 1717 词、法务页齐全、ToS 也没有禁止条款。

这说明：**这批提交的站点表面全都合格，问题在价值而非表面合规性。**
L2 的真实作用是产出 44 份事实档案（词数、法务页、统计 ID、GitHub 仓库数据、是否需要注册），
供 L3 精确调度；**筛选职责 100% 落在 L3**。下面这些踩过的坑，比通过率更有价值。

##### L2 踩坑记录（四个真实错误，全部已修正）

1. **跨行正则把全是 Allow 的 robots.txt 当成全域禁止** —— influence.so 有 147 个链接的正规站因此被判死。改成按 `User-agent` 块解析，同段存在任何 Allow 就不算。
2. **把整份 ToS 当纯文本扫，连页脚产品名都算进去** —— mydentify.com 是一款「AI Crawler Access Checker」，页脚徽章里的产品名命中了 `crawler` 就被淘汰。改为剥离 nav/footer/header/svg 只看正文，且正则必须带禁令语境（`no crawler` / `you may not use ... crawler`），不许裸词匹配。
3. **「无定价页」把 12/13 的免费工具全推向人工复核** —— 免费工具本来就没有定价页。改为只对声称 `freemium/paid` 的站点要求定价页。
4. **403 与超时又被当成死站**（L1 踩过的坑在 L2 复发）—— 改为只有明确 4xx 才淘汰，403/429/timeout 一律降级复核。

另外，**静态检测 AI 供应商引用命中率 0/8**，因为绝大多数站点在服务端调模型，
前端 HTML 里只出现自己的 `/api` 路径。该指标已降级为纯记录，不参与判定。

### L3 浏览器实操 —— 已交付（`scripts/try-tool.mjs`）

Playwright 1.60 + 本机 Chrome，串行访问，单站点预算 120 秒。**做的是探索式取证，不是硬编码选择器**——
每个工具的 UI 都不一样，写死选择器等于只能测三个站。

流程：打开 → 探测可交互元素 → 上传合成素材 / 填入提示词 → 勾选前置确认项 →
重采集按钮（新增Strategy，见下）→ 点主 CTA → 轮询等产物 → 抓字节落盘。

产出 `reports/evidence/<host>/`：`01-landing.png` · `02-result.png` · `artifact-*`（真实产物字节），
外加 `reports/evidence/<host>.json` 的完整观测记录。

#### 判定口径：没有字节就没有 VERIFIED

这是整套系统最容易失守的地方，所以把规则写死并实现进代码：

| 信号 | 强度 | 说明 |
|---|---|---|
| 抓到产物字节 ≥8KB | 强 | **唯一能直接给 VERIFIED 的东西** |
| 出现下载链接 | 强 | 同上 |
| 严格结果框里的文字 ≥120 字符 **且伴随后端调用** | 强 | 防止把营销文案当产物 |
| 检出模型供应商 / 有 POST 调用但没取回产物 | 弱 | 只能给 PARTIAL |
| 什么都没有 | — | UNVERIFIED，**不许补写** |

反例（都是真实踩过的坑，不是假设）：一次 `POST /api/projects` 返回 JSON 不等于产出，
它常常只是「创建项目」。把它判成 VERIFIED 会让整套输出失去意义。

#### 五个实现要点，每一个都是试跑时发现并修掉的

1. **重新采集按钮列表**——上传后页面会重排，按钮还会从 disabled 变可用。沿用上传前的 index 会点错元素。
   配套还要按「离输入位的距离」「是否在 nav/footer」「文案词数」打分，否则「Remove vocals」会和
   「Remove source image」（清空按钮）打平。
2. **必须勾选前置确认项**——vocalseparator.com 的主按钮要等「我拥有这段素材」勾上才可用。
   不处理它，这个真正能用的工具会被判成「找不到主按钮」。（跳过营销类勾选。）
3. **产物要走三条路径抓**：网络响应体、`<img>`、`<audio>/<video>`。只抓 `<img>` 会漏掉整个音频品类。
4. **图片要过 320px 尺寸门槛**——否则搜索结果页的 22 张 logo 缩略图会被当成「AI 产物」，直接制造假阳性。
5. **供应商名单要包含产物 CDN 域名**——`replicate.delivery` 比 `replicate.com` 强得多，
   命中前者意味着「产物确实是从 Replicate 的模型里出来的」，这是官网不会告诉读者的一手信息。
6. **结果容器必须剔除 `main`/`article`**——否则整页营销文案会被当成生成结果写进报告，污染 PARTIAL 判定。
   容器还要有长度上限（6000 字符），并要求「之前几乎没内容、之后有了内容」才认。

遇到以下任一情况立即停止，不许改写也不许重试第三次：
验证码（Turnstile / reCAPTCHA / hCaptcha）、任一支付字段、手机实名、IP 风控封禁。
另外页面自己报错（`generation failed` 等）会被记成 `FAILED`——**这是有效负面证据，不是失败**。

### L4 合成与发布
只有 `VERIFIED` 才生成页面。

写入现有表字段，**不需要改表结构**：
`verified=1` · `last_verified=<ISO>` · `reviewer_note=<证据摘要>` · `data_source='agent_l3'`

## 四、身份层：邮箱寻址与节流机制

真实试用 = 真实注册。**不做模拟注册，不伪造流量。**

用户决策：**沿用同一个邮箱，但每天只注册若干个**。以下是在这个决策下的最优实现。

### 关键选择：plus 寻址——它就是「同一个邮箱」

若邮箱来自 Gmail / Outlook / iCloud / Fastmail 等，`you+<tag>@gmail.com` 与「同一个邮箱」完全等价：
**同一账号、同一收件箱、来信照样进 INBOX**，风控看到的主体也相同。只是每封信的收件地址多了一个 tag。

于是三条风险里有两条被消掉，且不牺牲你的决策：

| 风险 | 纯同一邮箱 | plus 寻址 |
|---|---|---|
| 短时间集中注册触发风控 | 节流可缓解 | 节流可缓解（同样有效） |
| 哪个站泄露了无法区分 | 只能整体废弃，**不可逆** | 看邮件头的收件地址即可反查，单独封禁该 tag |
| 同一站点重复注册 | 靠记录 | tag 由 host 确定性派生，天然不会重复 |

代价：少数站点会在表单里拒绝 `+` 号，或自动剥掉 tag（两者目前均未在本队列中出现）。
遇到时该站退回 `UNVERIFIED`，不要为此改用别的方式重复尝试。

配置：`IDENTITY_MODE=plus` + `IDENTITY_EMAIL_BASE=you@gmail.com`。
若日后愿意投入一个独立域名，改 `IDENTITY_MODE=catchall` 即可，代码路径已预留。

### 每日配额：硬约束而非提醒

`IDENTITY_DAILY_QUOTA`（默认 4）。**计数基准是身份签发日**——签发之后紧接着就去注册，
只有卡在签发这一步，节奏才真的守得住。

```
node scripts/lib/identity.mjs --quota     查看今日剩余
node scripts/lib/identity.mjs --gen x.com 签发身份（达上限直接报错）
node scripts/lib/identity.mjs --claim x.com --note "…"  标记已注册
```

### 实测的队列规模（决定了这个节奏要多长）

对 L2 通过站点的注册需求分析：**30 个入口站点中，14 个找不到注册/登录入口，大概率免注册即可试。**
真正需要注册的只有 16 个 —— 按每天 3-4 个，**一周内走完，中间不需要任何熬夜**。

**执行顺序建议：先把那 14 个免注册的跑完。** 它们不需要邮箱、不消耗配额、今天就能出证据，
而且能先验证 L3 这一层到底能不能拿到想要的东西。确认可行后，再启动 16 个的分日注册队列。

### 配套

| 项 | 做法 |
|---|---|
| 接码 | IMAP 轮询收件箱，正则提验证链接 / 6 位验证码，超时 90 秒放弃 |
| 密码 | 每站独立，含大小写数字符号，写入本地凭据库 |
| persona | **全站统一**。同一个邮箱却各站换名字，反而更像脚本生成的账户 |
| 测试素材 | 一律用本地合成素材（生成的图片、音频、文本），**不上传任何私人文件** |
| 凭据库 | `reports/.identity-vault.json`，chmod 600 且已 gitignore |

### 三条红线（不可协商）

| 红线 | 理由 |
|---|---|
| **不解验证码** | 不用打码平台、不用视觉模型绕 Turnstile/reCAPTCHA。这是明确的技术对抗行为，性质与批量注册完全不同。碰到即停。 |
| **不填任何支付信息** | 信用卡、PayPal、实名认证一律停。含"免费试用需绑卡"的站点，直接 `UNVERIFIED`。 |
| **不上传私人文件** | 只用合成素材。未知站点对个人文件的处理完全不可控。 |

### ToS 闸门：实测效果要说实话

原计划用 ToS 自动化条款做一层「免费筛选」。**实测 39 份条款拉取成功，命中 0 条**——
之前判出的 3 条全是误杀（详见第五章的踩坑记录）。

所以它**不是筛选器**，但仍然保留：价值变成了**合规确认**——确认这批站点里没有明确禁止自动化访问的，
让我们可以放心继续。保留 ToS 检查但不指望它过滤。

### 成功率预期（先说实话）

16 个需注册的站点里，预计约 6 成能注册成功并拿到免费额度，其余卡在验证码 / 绑卡 / 风控。

因此**不要指望注册机制能救活全部**。它把 L3 的可测范围从 14/30 提到约 24/30，
剩下的仍必须诚实记为 `UNVERIFIED`。

## 五、三种结局（关键设计）

图里的三出口不是为了好看。**中间那个 UNVERIFIED 是整套系统诚实与否的分水岭。**

| 结局 | 触发条件 | 产物 |
|---|---|---|
| `VERIFIED` | 拿到真实产物，且 L2 无重大疑点 | 生成页面 + 证据包截图 |
| `UNVERIFIED` | 站活着但拿不到证据（登录墙 / 付费墙 / 反爬） | **不发布**，留证据待人工或复检 |
| `REJECTED` | L1/L2/L3 任一层淘汰 | 不发布，附具体理由 |

**绝对的禁令：`UNVERIFIED` 永远不能被写成 `VERIFIED`。**
"跑不通"必须如实记成"跑不通"。一旦开始给它编数据，这套系统的全部信用立刻归零，
而且归零的方式是静默的——你会发布一批看起来很有据实则虚构的页面，比现在更糟。

## 六、证据 Schema

`reports/evidence/<host>.json`，后续直接喂给 L4：

```json
{
  "host": "vocalseparator.com",
  "pr": 76,
  "verdict": "VERIFIED",
  "observed_at": "2026-10-28T08:00:00+08:00",
  "evidence": {
    "runs_without_signup": true,
    "steps": ["打开首页", "上传 3.2MB wav", "点击 Split", "等待完成"],
    "wall_clock_sec": 47,
    "output_kind": "audio/zip",
    "screenshots": ["evidence/vocalseparator.com/before.png", ".../after.png"],
    "api_providers_seen": ["replicate.com"],
    "free_limit_observed": "第 3 次后要求注册",
    "claim_vs_actual": "自称 15 秒，实测 47 秒"
  }
}
```

`claim_vs_actual` 这一项是整套东西唯一的价值来源——它写出来的每一行都是官网没有的。

## 七、实施顺序

**每步独立可交付，任何一步做完停下都不亏：**

- **P1** `scripts/probe-evidence.mjs`（L2）—— 跑通 46 条，看淘汰率。这是最重要的一步，因为它零成本且决定后续要不要投入。
- **P2** `scripts/try-tool.mjs`（L3）—— 先跑 **5 条**验证证据质量，再决定是否铺到全部。
  身份层（一次性别名 + IMAP 接码）在 P2 引入，**不要更早**——若 P1 已证明大部分站点在 L2 就该淘汰，
  就没必要为一个会缩小的集合搭建接码逻辑。
- **P3** `scripts/publish-verified.mjs`（L4）—— 合成 markdown + 写入 D1。
- **P4**（可选）把 L1/L2 合并进 `link-checker` cron，作为新提交的自动前置门禁。

## 八、验收指标

提前写死，避免事后给自己找台阶：

| 指标 | 门槛 |
|---|---|
| L2+L3 综合通过率 | 必须落在 20%–45%。高于 45% 说明闸门太松，低于 20% 说明规则误杀 |
| 每条已发布页面的一手信息行数 | ≥ 3 行（实测耗时 / 实测额度 / 产物类型 / 声明 vs 实测） |
| 单次全量运行 | ≤ 45 分钟机器时间，人工介入 0 次 |
| 误杀检查 | 已发布页面中随即抽 3 条人工复核，必须能通过 |

**第一次跑完 P2 要回到这张表对照。如果通过率不在这个区间，先修规则，不要往下走。**
